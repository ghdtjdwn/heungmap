# 서비스 명세

## 핵심 개념

축제 수요를 정성 판단만으로 추정하지 않고 데이터로 예측합니다. 하나의 예측 엔진이 기획자와
방문객에게 각자 필요한 정보를 제공합니다.

```text
                  ┌─────────────────────────┐
   기획자 입력 ──▶ │  흥행 예측 엔진 (HeungMap)  │ ──▶ 방문객 정보
 (지역·시기·규모·   │  방문자 수 / 흥행 점수 / 근거 │     (혼잡·티켓 경쟁도·
  테마·출연 등)     └─────────────────────────┘      주변 주차/숙소/코스)
```

기획자가 등록한 축제 정보는 방문객 화면의 탐색 데이터로 이어집니다.

## 사용자

| 사용자군 | 상황과 문제 | 필요한 도움 |
| --- | --- | --- |
| 축제·콘서트·행사 이용객 | 방문 전에 혼잡도, 티켓 수요, 이동·주차·숙박 정보를 여러 곳에서 찾아야 함 | 예상 수요와 주변 정보를 한 흐름에서 확인 |
| 대형 행사·콘서트 기획자 | 지자체, 공연기획사, 행사 대행사 등이 큰 예산을 집행하기 전에 수요와 장소 적정성을 검토해야 함 | 예상 수요, 영향 요인, 장소 규모와 편의시설 보완점 |
| 소규모 독립 기획자·가수 | 홍대 클럽 같은 소규모 공연장이나 독립 공연에서 자본과 시장 정보가 부족한 상태로 직접 기획해야 함 | 제한된 예산 안에서 시기·장소·규모의 위험을 비교하고 우선 보완할 항목 확인 |

공모전의 첫 검증·구현 범위는 TourAPI와 지역별 방문자 데이터로 설명 가능한 **축제와 지역 행사**다.
콘서트와 소규모 클럽 공연은 같은 의사결정 구조를 적용할 확장 대상이지만, 공연별 수요 데이터와
라벨을 별도로 확보·검증하기 전에는 현재 지원 기능이나 모델 성능으로 주장하지 않는다.

## 기능 명세

### 기획자 모드

1. 축제 조건 입력: 지역, 개최 시기, 기간, 예상 규모, 테마·카테고리, 선택적 출연진·프로그램
2. 수요 예측: 예상 방문자 수와 흥행 점수 산출. 초기에는 규칙 기반, 데이터가 검증되면 ML 모델 사용
3. 예측 근거: 점수에 영향을 준 요인 제공. 모델 단계에서는 SHAP 적용 검토
4. 개최지·편의시설 제안: 후보지 주변 주차장·숙박·접근성 정보를 TourAPI와 지도에서 조회
5. 기획 보완 리포트: 약점 요인과 개선안을 구조화하고, 선택적으로 LLM이 설명 문장을 생성

전체 입력 후보, 예측 모델·근거 데이터·LLM의 처리 순서와 기획자 담당 범위는
[`PLANNER_WORKFLOW.md`](PLANNER_WORKFLOW.md)에서 관리합니다.

### 방문객 모드

1. 축제 탐색: 기획자가 공개한 축제와 TourAPI `searchFestival2` 목록 제공
2. 수요 지표: 예측 방문자 수를 바탕으로 예상 혼잡도와 티켓 수요 지표 제공
3. 주변 정보: 주차장, 숙소와 연계 관광지를 TourAPI 위치 기반 정보로 제공
4. 방문 코스: 지도 위에 이동 동선과 주변 즐길 거리를 표시

## 제품 설계의 특징

1. 추천 문장만 생성하지 않고 재현 가능한 데이터 조립과 예측 baseline을 먼저 구축합니다.
2. 기획자와 방문객을 하나의 예측 결과로 연결해 입력과 탐색 흐름을 분리하지 않습니다.
3. 예측값, 계산 근거와 생성 문장을 구분해 사용자가 정보의 출처를 확인할 수 있게 합니다.

## 기대 효과

- 대형 기획자: 흥행 실패와 예산 낭비 위험을 사전에 확인하고 개최지와 편의 구성을 보완
- 소규모 독립 기획자·가수: 제한된 자본과 정보로 직접 기획할 때 시기·장소·규모 대안을 같은 기준으로 비교
- 이용객: 혼잡과 티켓 수요의 불확실성을 줄이고 주변 이동 계획을 한 화면에서 확인
- 지역 운영자: 지역별 축제 수요와 편의시설 부족 신호를 일관된 기준으로 비교

## 최소 기능 경계

- 기획자: 조건 입력, 규칙 기반 흥행 점수, 후보지 주변 편의시설 표시
- 방문객: 실제 축제 목록, 예상 혼잡도, 주변 주차·숙소 지도
- 최소 기능이 end-to-end로 동작하고 데이터 출처가 확인된 뒤 학습 모델과 생성형 리포트를 추가합니다.
