# 전달 단계와 범위 조정 기준

## 단계적으로 전달하는 이유

데이터 조립, 예측 모델과 웹 애플리케이션은 실패 조건과 검증 방법이 서로 다릅니다. 각 단계가 독립적으로
실행 가능한 상태를 만들고, 데이터 품질이 확인된 뒤에만 복잡도를 높입니다.

## 단계별 범위

| 단계 | 구현 범위 | 완료 조건 |
| --- | --- | --- |
| 데이터 검증 | TourAPI 축제 정보와 지역·기간별 방문자 시계열 수집·결합 | label 의미, 행 수, 결측률과 결합률 기록 |
| 기반 제품 | 규칙 기반 점수, 입력·결과 화면, TourAPI 연동, 주차·숙소 지도 | 기획자와 방문객 흐름을 로컬에서 end-to-end 실행 |
| 예측 모델 | 지역 수요 baseline, 행사 uplift, LightGBM 회귀, 예측 범위와 추론 API | 시간·group 검증을 재현하고 단순·규칙 baseline 대비 결과와 오차 범위 기록 |
| 설명과 개선 | SHAP 영향 요인, 선택적 LLM 설명, 사용자 화면 개선 | 계산 결과와 생성 문장을 분리하고 장애 시 fallback 제공 |

한 단계의 완료 조건을 충족하기 전에는 다음 단계의 의존성을 제품 경로에 추가하지 않습니다.

## 구현 순서

1. API 이용 조건과 응답 schema를 확인합니다.
2. 수집·정제·결합 파이프라인과 품질 보고서를 만듭니다.
3. 규칙 기반 baseline과 두 사용자 화면을 연결합니다.
4. 학습 데이터가 충분할 때만 LightGBM을 학습하고 baseline과 비교합니다.
5. 예측 근거와 설명 기능을 추가하고 실패 fallback을 검증합니다.
6. 자동화된 테스트, 운영 설정과 배포 절차를 정의합니다.

## 범위 조정 규칙

축소가 필요하면 선택적 설명 기능, 모델 해석, 학습 모델 순서로 제외합니다. 다음 항목은 유지합니다.

- TourAPI 기반 축제 탐색과 주변 관광 정보
- 출처와 계산 방식이 확인되는 수요 지표
- 기획자 입력에서 방문객 탐색까지 이어지는 최소 사용자 흐름
- 데이터 부족이나 외부 API 실패를 숨기지 않는 오류 처리

축제 단위 label을 설명하기 어렵다면 지역·기간별 관광 혼잡 예측으로 범위를 전환하고, 동일한 수집·결합
파이프라인을 재사용합니다.
