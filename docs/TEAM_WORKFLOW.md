# 2인 역할 분담과 작업 시작 절차

## 현재 결정

- 팀원 두 명은 기술 계층이 아니라 **기획자 기능**과 **사용자 기능**을 기준으로 역할을 나눈다.
- 각 담당자는 자기 사용자 흐름의 화면, API 연동, 오류 처리, 테스트와 문서를 end-to-end로 책임진다.
- 담당자 이름은 아직 정하지 않았다. 정해지는 즉시 아래 표의 `TBD`를 실제 이름으로 바꾼다.
- 사용자 기능의 UI/UX 기준 서비스는 [EVENT-US](https://event-us.kr/)다.
- 사용자의 요청에 따라 EVENT-US 공개 화면 조사는 역할 확정 전에는 진행하지 않는다. 현재 저장소의 문서도 실제 화면을 확인했다고 주장하지 않는다.

## 역할 배정표

| 책임 | 담당자 | 최종 책임 범위 |
| --- | --- | --- |
| 기획자 기능 담당 | TBD | 기획 조건 입력부터 수요 결과·근거·보완점까지 전체 흐름 |
| 사용자 기능 담당 | TBD | 행사 탐색부터 캘린더·지도·상세·주변 정보까지 전체 흐름 |
| 공유 데이터·예측 계약 관리자 | TBD — 위 두 명 중 1명 | 공통 schema, feature, model, score·prediction 정의와 변경 관리 |
| 통합 검토자 | TBD — 계약 관리자가 아닌 팀원 | 상대 영역 PR 검토와 두 흐름 통합 확인 |

데이터·예측 계약 관리자와 통합 검토자는 별도 인원이 아니라 두 명이 함께 맡는 교차 책임이다. 한 사람이
공통 계약을 관리하면 다른 사람이 변경을 검토해 두 사용자 화면의 지표가 달라지는 일을 막는다.
모델 담당 범위와 입력·출력 후보는 [`MODEL_PLAN.md`](MODEL_PLAN.md)를 기준으로 역할을 정한다.

## 기획자 기능 담당

### 사용자 흐름

1. 행사 유형, 지역, 시기, 기간, 예상 규모와 테마를 입력한다.
2. 규칙 기반 baseline 또는 검증된 모델로 예상 수요와 흥행 점수를 계산한다.
3. 점수에 영향을 준 요인과 데이터 출처를 확인한다.
4. 개최지 주변 주차·숙박·접근성 정보를 확인한다.
5. 대형 기획자는 장소와 편의시설 보완점을, 소규모 독립 기획자·가수는 제한된 예산에서 우선 조정할 시기·장소·규모를 확인한다.

### 첫 작업 목록

- [ ] 대형 기획자와 소규모 독립 기획자·가수의 대표 시나리오를 각각 1개 작성
- [ ] 입력 필드와 필수·선택 여부 정의
- [ ] 입력→계산→결과 화면 wireflow 작성
- [ ] 규칙 기반 score 응답 계약을 공유 schema와 맞춤
- [ ] 로딩, 잘못된 입력, 데이터 없음과 외부 API 오류 상태 정의
- [ ] 입력부터 결과까지 최소 흐름 구현과 테스트

### 완료 조건

- 한 번의 데모에서 조건 입력부터 결과와 근거 확인까지 중단 없이 실행된다.
- 표시한 수치가 실제값·추정값·예측값·상대지수 중 무엇인지 구분된다.
- 대형·소규모 기획자에게 제공하는 가치가 같은 문구의 반복이 아니라 각 상황에 맞게 설명된다.
- 외부 API가 실패해도 오류 원인과 다시 시도할 방법을 사용자가 이해할 수 있다.

## 사용자 기능 담당

### 목표 사용자 흐름

1. 축제·콘서트·행사를 날짜와 지역 기준으로 탐색한다.
2. 행사 캘린더에서 날짜별 행사를 비교한다.
3. 행사 지도에서 위치와 주변 행사를 탐색한다.
4. 필터와 검색 결과를 캘린더·지도에서 일관되게 유지한다.
5. 행사 상세에서 일정, 장소, 예상 수요·혼잡도와 주변 주차·숙박·연계 관광지를 확인한다.

### EVENT-US 벤치마킹 계획

담당자가 정해지면 사용자 기능 담당이 EVENT-US의 공개 행사 캘린더와 행사 지도를 직접 조사한다. 목표는
두 기능의 정보구조, 탐색 순서와 상호작용을 흥할지도 사용자 모드의 기준으로 삼는 것이다.

조사 결과로 다음을 기록한다.

- [ ] 캘린더·지도·행사 상세로 이어지는 전체 page flow
- [ ] desktop·mobile의 화면 구성과 breakpoint별 변화
- [ ] 검색, 날짜, 지역, 카테고리와 정렬 filter
- [ ] 캘린더 날짜 선택, 지도 이동·확대, marker 선택과 목록 동기화
- [ ] URL과 query parameter에 보존되는 상태
- [ ] 로딩, 빈 결과, 위치 권한 거부와 오류 상태
- [ ] 반복되는 component와 예상 데이터 schema
- [ ] 접근성, keyboard 조작과 반응형 동작
- [ ] 흥할지도에서 그대로 채택할 구조와 변경할 부분

### 구현 원칙

- 공개 화면에서 확인한 캘린더·지도 중심의 정보구조와 사용자 흐름을 최대한 가깝게 재현한다.
- EVENT-US의 비공개 architecture나 source code를 확인했다고 가정하지 않는다. 공개 동작을 근거로 흥할지도 기술 스택에서 독립 구현한다.
- EVENT-US의 상호, logo, 문구, image, icon과 source code를 복사하지 않고 흥할지도 브랜드와 자체 component를 사용한다.
- 조사 전에는 화면 구성이나 기술 구조를 확정하지 않는다. 확인한 사실과 추론을 분리해 기록한다.

### 첫 작업 목록

- [ ] EVENT-US 공개 화면 조사와 증거 기록
- [ ] 캘린더·지도 page inventory와 wireflow 작성
- [ ] 행사 목록·상세·필터·지도 marker에 필요한 공통 schema 제안
- [ ] mock data로 캘린더와 지도 탐색 흐름 구현
- [ ] TourAPI `searchFestival2` 응답을 공통 schema로 연결
- [ ] 로딩, 빈 결과, 지도 오류와 위치 권한 거부 처리
- [ ] desktop·mobile 핵심 흐름 테스트

### 완료 조건

- 같은 검색·날짜·지역 filter가 목록, 캘린더와 지도에 일관되게 적용된다.
- 캘린더 또는 지도에서 행사를 선택해 상세 정보와 주변 정보를 확인할 수 있다.
- browser 새로고침이나 공유 URL에서도 필요한 탐색 상태가 유지된다.
- EVENT-US와 비교한 기능·화면 상태 점검표가 있고, 미구현 차이를 숨기지 않는다.
- TourAPI 사용 지점과 흥할지도 자체 예측 지표가 화면에서 명확히 구분된다.

## 공동 작업 — 역할 분담 전에 먼저 합의할 것

두 흐름이 같은 데이터를 사용하므로 다음 항목은 한쪽이 단독으로 확정하지 않는다.

| 공유 대상 | 최소 필드·결정 |
| --- | --- |
| 행사 | `event_id`, 출처, 이름, 유형, 시작·종료 일시, 지역 코드, 주소, 좌표, 대표 이미지 |
| 장소 | `venue_id`, 이름, 주소, 좌표, 수용 규모와 주변 시설 |
| 수요 결과 | 값, 단위, 실제·추정·예측 구분, 기준 시점, confidence 또는 한계 설명 |
| 탐색 filter | 검색어, 날짜 범위, 지역, 행사 유형과 정렬 |
| 출처 | TourAPI 등 source 이름, 원본 식별자, 갱신 시각과 이용조건 |
| 오류 | 오류 코드, 사용자 메시지, 재시도 가능 여부와 fallback |

공통 계약은 별도 version으로 관리하고 변경 PR에는 양쪽 화면의 영향을 적는다. 계약 변경은 상대 담당자의
검토 없이 병합하지 않는다.

## 권장 진행 순서

1. 두 담당자 이름과 공유 데이터·예측 계약 관리자를 정한다.
2. 두 명이 함께 데이터 검증 게이트를 통과시키고 행사·수요 지표의 의미를 확정한다.
3. 공통 schema v1과 mock response를 합의한다.
4. 기획자 담당과 사용자 담당이 mock data 기반 최소 흐름을 병렬로 만든다.
5. 실제 TourAPI와 규칙 기반 score를 연결한다.
6. 상대 담당자가 PR을 검토하고 두 흐름의 용어·수치·오류 처리를 맞춘다.
7. 매주 하나의 end-to-end demo를 실행하고 심사기준 점검표를 갱신한다.

## Git 협업 규칙

- 기획자 기능: `feat/planner-*`
- 사용자 기능: `feat/visitor-*`
- 공유 계약·인프라: `chore/shared-*` 또는 변경 성격에 맞는 prefix
- 한 PR은 한 사용자 흐름 또는 한 공통 계약 변경만 포함한다.
- 자기 PR은 상대 담당자가 검토한 뒤 병합한다.
- 공통 파일을 동시에 수정해야 하면 먼저 담당 범위와 병합 순서를 정한다.
- API key, 원본·가공 데이터, model artifact와 build output은 commit하지 않는다.

## 공통 완료 정의

- [ ] 담당 사용자 시나리오가 end-to-end로 동작한다.
- [ ] 정상·로딩·빈 결과·오류 상태가 구현되고 확인됐다.
- [ ] 공통 schema와 실제 화면의 필드가 일치한다.
- [ ] 데이터 출처와 수치의 의미·한계가 표시된다.
- [ ] desktop·mobile 핵심 흐름을 확인했다.
- [ ] 상대 담당자가 PR과 사용자 흐름을 검토했다.
- [ ] 실행 방법과 실제 검증 결과를 문서에 갱신했다.
- [ ] 1차·최종 심사기준 중 어떤 항목을 강화하는지 설명할 수 있다.
