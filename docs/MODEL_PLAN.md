# AI 수요 예측 모델 계획

## 목적과 현재 상태

흥할지도의 핵심 AI는 문장을 생성하는 LLM이 아니라 **행사 전 정보를 이용해 수요와 위험을 예측하는
공유 엔진**이다. 같은 예측 결과를 기획자 화면에서는 장소·규모·편의시설 의사결정에, 사용자 화면에서는
혼잡도·티켓 수요·방문 계획에 사용한다.

2026-09-06 데이터 게이트에서 TourAPI 축제 원본 688건과 지역 방문자 464,092행을 수집해 514건·76.37%를
결합했습니다. 게이트는 통과했지만 LightGBM이 채택 기준을 통과하지 못해 제품은 규칙 mock을 유지합니다.
이 문서의 입력값은 가능한 후보를 넓게 기록한 목록이며, 실제 모델에 전부 넣는다는 뜻이 아닙니다. 상세 수치와 분류는
[`DATA_GATE_REPORT.md`](DATA_GATE_REPORT.md)에 있고 다음 조건을 통과한 항목만 사용합니다.

- 예측 시점에 실제로 구할 수 있음
- 출처와 이용조건이 명확함
- 학습과 서비스에서 같은 정의로 재현 가능함
- label을 직접 또는 간접으로 누설하지 않음
- 결측률과 표본 수가 모델 검증에 적합함
- 실제 사용자 의사결정에 의미가 있음

## 예측 목표 우선순위

| 우선순위 | label 후보 | 사용할 수 있는 조건 | 사용자에게 표시할 표현 |
| ---: | --- | --- | --- |
| 1 | 주최 측 공식 관람객·입장 집계 | 행사별 정의와 집계 방식이 일관되고 충분한 표본 확보 | 예상 관람객 범위 |
| 2 | 검표·예매·판매량 | 유료 행사의 판매·취소·수용인원 정의가 일관됨 | 예상 입장·판매 수요 범위 |
| 3 | 행사 기간 지역 방문수요 증가분 | 동일 지역의 평상시 기준선을 방어 가능한 방식으로 계산 | 평상시 대비 방문수요 증감률 |
| 4 | 검증된 여러 지표의 합성 score | 절대 label 확보 실패, 구성 지표와 가중치 설명 가능 | 흥행 가능성·혼잡 score |

지역 방문자 수는 특정 행사 관람객과 같지 않다. 3번이나 4번을 사용할 때는 `예상 관람객 수`라고
표시하지 않고 `지역 방문수요`, `증감률`, `상대지수`로 구분한다.

## 권장 모델 구조

```text
TourAPI 행사 정보 ─┐
관광 데이터랩 ─────┼─▶ 지역 평상시 수요 baseline ─┐
날짜·날씨·입지 ────┘                              │
                                                   ├─▶ 최종 수요 범위·score·혼잡 등급
행사 규모·테마·장소·프로그램 ─▶ 행사 uplift 모델 ─┘
                                                   │
                                                   └─▶ 영향 요인·신뢰도·한계
```

1. **규칙 baseline**: 주말, 계절, 지역 과거 수요와 행사 규모에 설명 가능한 가중치를 적용한다.
2. **지역 평상시 수요 모델**: 행사가 없다고 가정했을 때 해당 지역·시기의 기본 방문수요를 예측한다.
3. **행사 uplift 모델**: 행사 특성이 평상시 수요를 얼마나 올리거나 내리는지 LightGBM으로 학습한다.
4. **불확실성 모델**: 가능하면 quantile 예측으로 낮은 값·중앙값·높은 값 범위를 계산한다.
5. **설명 계층**: 검증된 모델에만 SHAP을 적용하고, LLM은 계산 결과를 쉬운 문장으로 바꾸는 데만 사용한다.

표본이 부족하면 2~4번을 억지로 학습하지 않고 규칙 baseline을 제품에 사용한다. 딥러닝과 복잡한 ensemble은
표 형태의 학습 데이터와 검증 표본이 충분하다는 증거가 생기기 전에는 도입하지 않는다.

## 입력값 후보 전체 목록

### 1. 식별·출처·기준 시점

다음 값은 결합과 재현에는 필요하지만 모델 입력에서는 제외될 수 있다.

- `event_id`, TourAPI `contentid`, 원본 source ID
- 원본 제공기관과 API 이름
- 데이터 수집·갱신 시각
- 예측 기준일과 행사일까지 남은 일수
- 데이터 schema·feature·model version
- 원본·가공 레코드의 품질 상태

### 2. 행사 기본 정보

- 행사 유형: 축제, 콘서트, 공연, 전시, 컨퍼런스, 체험, 지역 행사 등
- 주제·테마·TourAPI 대·중·소분류
- 무료·유료 여부와 티켓 가격 구간
- 단일 행사·반복 행사·연례 행사 여부
- 신규 행사 여부와 개최 횟수
- 행사 시작·종료 일시와 전체 기간
- 일별 운영 시작·종료 시각
- 실내·실외·혼합 여부
- 단일 장소·다중 장소 여부
- 전체 프로그램·공연·부스·세션 수
- 예상 관객 규모와 목표 관객 유형
- 가족·아동·청년·중장년·외국인 등 대상층
- 사전 예약 필요 여부와 현장 참여 가능 여부
- 행사 설명 길이, 제공 이미지 수와 정보 완성도
- 주최 유형: 지자체, 공공기관, 기업, 공연기획사, 독립 기획자·가수 등

### 3. 일정·달력

- 개최 연도·분기·월·주차·계절
- 시작·종료 요일
- 포함된 평일·주말·토요일·일요일 수
- 공휴일·대체공휴일·연휴 포함 여부와 연휴 길이
- 방학·휴가철·성수기·비수기 여부
- 낮·저녁·심야 시간대
- 일출·일몰 전후 여부
- 행사 준비 시점에서 개최일까지 남은 기간
- 전년도 동일 행사·동일 지역 행사의 개최 시기 차이
- 코로나19·사회적 거리두기처럼 구조적 단절을 나타내는 기간 구분

### 4. 지역·공간

- 광역지자체·기초지자체·행정동 코드
- 법정동 코드와 TourAPI 지역 코드
- 위도·경도와 geohash 등 공간 식별값
- 수도권·광역시·도시·농촌·도서 지역 구분
- 도심·상업·주거·관광·공원·수변 등 입지 유형
- 지역 인구, 인구밀도와 연령대별 인구
- 유동인구·생활인구 등 공개 집계값
- 지역 관광사업체·숙박시설·음식점 밀도
- 인근 지역 경계와 주요 배후도시까지 거리

### 5. 장소·수용 규모

- 장소 유형: 야외광장, 공원, 경기장, 공연장, 클럽, 전시장 등
- 공식 수용인원과 기획자 예상 수용 규모
- 좌석·스탠딩·혼합 여부
- 행사장 면적과 출입구 수
- 실내·실외·우천 대체 공간 여부
- 주차 가능 대수와 행사장까지 거리
- 가장 가까운 지하철·기차·버스 정류장 거리
- 대중교통 노선 수와 막차 시각
- 고속도로 IC·공항·철도역까지 거리
- 보행 접근성, 경사·무장애 이동 가능 여부
- 화장실·휴식·의료·안전·수유·물품보관 시설
- 행사장 주변 소음·영업시간·수용 제한 등 공개 운영 조건

### 6. TourAPI 행사·관광 정보

- `searchFestival2`의 행사명·기간·주소·좌표·지역·분류
- 행사 상세 소개, 주최·주관, 문의처와 홈페이지 제공 여부
- 대표·추가 이미지 유무와 수
- 위치 기반 주변 관광지·문화시설·레포츠·쇼핑·음식점·숙박 수
- 반경별 주변 POI 수: 예시 500m, 1km, 3km, 5km
- 가장 가까운 숙박·음식점·관광지까지 거리
- 관광지별 연관 관광지 순위와 연결성
- 기초지자체 중심 관광지 순위와 중심성
- 무장애·반려동물·웰니스·고캠핑 등 행사 테마와 맞는 주변 자원

### 7. 한국관광 데이터랩 지역 수요

- 일·주·월 지역 방문자 수 또는 제공된 집계값
- 1주·4주·12주·1년 전 lag
- 최근 4주·12주 이동평균·중앙값·최솟값·최댓값·표준편차
- 전주·전월·전년 동기 대비 증감률
- 같은 지역·요일·월·계절의 평상시 수요
- 현지인·외지인, 내국인·외국인 구성
- 방문자 유입·유출 지역 분포
- 숙박 방문자 비율과 평균 체류 관련 공개 지표
- 관광 소비금액과 숙박·음식·쇼핑·문화 등 업종별 소비 구성
- 내비게이션 목적지 검색량과 현지인·외지인 검색 분포
- 지역별 관광 수요 강도
- 지역별 관광 체류·소비 강도
- 지역별 관광 다양성
- 지역별 관광 자원·서비스·문화 자원 수요
- 관광지 집중률 방문자 추이 예측값

관광지 집중률 예측은 관광공사가 만든 별도 예측값이다. 흥할지도 모델의 정답으로 사용하지 않고, 예측
시점에 실제로 제공되는 경우에만 외부 benchmark 또는 사용자 화면의 보조 지표로 검토한다.

### 8. 날씨·환경

- 행사 시점의 예보 기온·최고·최저기온
- 체감온도, 습도와 풍속
- 강수 확률·예상 강수량·적설량
- 맑음·흐림·비·눈 상태
- 폭염·한파·태풍·미세먼지·기상특보
- 과거 평년 대비 기온·강수 편차
- 실외 행사에 대한 날씨 민감도
- 일몰 시각과 야간 행사 여부

예측 서비스가 D-30, D-7, D-1처럼 여러 시점에 제공된다면 각 시점에 실제로 사용할 수 있는 예보만 사용하고
행사 후 관측 날씨를 과거 예측에 섞지 않는다.

### 9. 교통·접근성·주변 편의

- 지역 간 예상 이동시간과 거리
- 대중교통 접근성 score
- 지하철·버스·철도 배차 빈도
- 주변 도로·주차 수용력과 혼잡 관련 공개 지표
- 숙박·음식점·카페·편의점·화장실 수와 거리
- 주변 관광지의 수·유형·인기도·중심성
- 행사 전후 연계할 수 있는 관광 코스 수
- 장애인·유아 동반·반려동물 접근 가능 시설 수

### 10. 공연자·프로그램·콘텐츠

- 출연진·가수·연사·팀 수
- 출연진 장르와 행사 테마 적합도
- 공개된 팔로어·구독자·검색 관심도
- 과거 공연의 장소 규모와 판매·관람 실적
- 헤드라이너·신인·지역 예술가 구성
- 프로그램 다양성, 유명 프로그램과 체험형 프로그램 비율
- 행사 소개 문장의 keyword·topic·text embedding
- 공개 이미지의 테마·품질 관련 feature

출연진 인기나 콘텐츠 embedding은 출처·이용조건과 표본 수가 확인된 뒤 추가한다. 이름 자체를 외우는
모델이 되지 않도록 새로운 출연진과 지역에서도 성능을 검증한다.

### 11. 경쟁 행사·대체 선택지

- 같은 날짜·지역의 다른 행사 수
- 반경별 동시 행사 수와 예상 규모 합계
- 같은 장르·대상층의 경쟁 행사 여부
- 가장 가까운 대형 경쟁 행사까지 거리
- 동일 출연진·유사 프로그램의 일정 충돌
- 프로스포츠 경기·대형 공연·지역 축제 동시 개최 여부
- 주변 상시 관광지의 계절 인기도

### 12. 홍보·온라인 관심도

- 예측 시점까지의 검색량과 증감 속도
- SNS 언급량·공유·저장·반응 수와 변화율
- 공식 홈페이지·상세 페이지 조회수
- 뉴스·블로그·커뮤니티 게시물 수
- 광고·홍보 예산과 채널 수
- 홍보 시작일부터 행사일까지의 기간
- 이메일·알림 신청, 관심 행사 저장 수
- 공식 계정 팔로어와 게시 빈도

행사 종료 후 발생한 검색·게시물·조회수는 학습 feature로 사용하지 않는다. 예측 시점별 snapshot을 저장할
수 있을 때만 사용한다.

### 13. 예매·가격·운영 계획

- 티켓 가격, 할인·무료 초대 비율
- 좌석·등급별 공급량
- 예매 시작일과 판매 기간
- 예측 시점까지 판매량·판매율·취소율·판매 속도
- 대기자·알림 신청·장바구니 등 공개 또는 합법적으로 확보한 선행 수요
- 행사 예산과 손익분기 관객 수
- 장소 대관비·출연비·홍보비 등 기획자가 직접 입력한 비용 구간
- 운영 인력, 안전 인력, 부스와 편의시설 계획
- 우천·출연 취소·장소 변경 fallback 보유 여부

예매 정보가 없는 무료 축제와 예매 정보가 있는 콘서트는 가용 feature가 다르다. 필요하면 `D-30`, `D-7`,
`D-1`처럼 예측 시점별 모델을 분리하며, 리셀 가격 예측은 범위에서 제외한다.

### 14. 주최자·행사 이력

- 주최자 유형과 과거 행사 수
- 동일 행사·브랜드의 개최 횟수
- 전년도 동일 행사 수요와 증감률
- 과거 장소·시기·규모 변경 이력
- 과거 취소·연기·매진 여부
- 과거 예측 오차와 데이터 품질
- 행사별 공식 집계 방식의 일관성

### 15. 파생·상호작용 feature

- 행사 기간 수요 ÷ 평상시 지역 수요
- 예상 규모 ÷ 장소 수용인원
- 주차 대수·숙박 객실·화장실 수 ÷ 예상 수요
- 주변 POI 수 ÷ 반경 면적
- 출연진 관심도 × 장소 수용인원
- 홍보 관심도 증가율 × 행사까지 남은 일수
- 강수 확률 × 실외 행사 여부
- 연휴 여부 × 숙박 가능 시설 수
- 지역 기본수요 × 행사 테마 적합도
- 경쟁 행사 예상 규모 ÷ 지역 평상시 수요
- 전년도 동일 행사 수요의 지역 전체 대비 비율
- 최근 수요 추세와 전년 동기 추세의 차이

상호작용 feature는 의미를 설명할 수 있고 교차검증에서 반복적으로 도움이 될 때만 유지한다.

## 사용하면 안 되는 입력

- 예측 대상 기간이 끝난 뒤 확정된 실제 방문자·매출·소비·검색·SNS 값
- 행사 종료 뒤 작성된 기사·후기·평점
- 취소된 행사 여부를 과거 예측 시점에 이미 알았던 것처럼 처리한 값
- label에서 직접 계산했거나 label과 사실상 동일한 값
- 미래 데이터로 계산한 이동평균·순위·정규화 값
- 수집 시점이 기록되지 않아 예측 당시 가용 여부를 알 수 없는 값
- 출처·이용허락범위가 불명확한 scraping 데이터
- 개인을 식별하거나 재식별할 수 있는 위치·통신·결제 데이터

## 출력값 후보 전체 목록

### 공통 예측 계약

실제 직렬화 field와 available·unavailable 응답은 [`SHARED_SPEC.md`](SHARED_SPEC.md)와
[`../contracts/openapi.yaml`](../contracts/openapi.yaml)을 기준으로 구현한다.

- `prediction_id`, `event_id`, 예측 기준시각과 대상 기간
- 예측 종류: 공식 관람객, 입장·판매 수요, 지역 방문수요, 상대 score
- 중앙 예측값 `p50`
- 보수적·낙관적 범위 `p10`, `p90`
- 평상시 지역 baseline과 행사 uplift 값·비율
- 흥행 가능성 score 0~100과 계산 version
- 혼잡 등급: 여유·보통·혼잡·매우 혼잡 등
- 티켓 수요 등급 또는 예상 판매율 범위
- 신뢰도·데이터 충분성 등급
- 학습 범위 밖 입력 여부와 경고
- 상승·하락 영향 요인과 영향 방향
- 사용한 데이터 출처, 갱신 시각과 model version
- 결과 해석 주의사항과 fallback 사용 여부

### 기획자용 출력

- 예상 수요와 불확실성 범위
- 장소 수용인원 대비 예상 점유율·초과수요 위험
- 목표 관객 대비 부족·초과 예상치
- 손익분기 관객 수 대비 위험도
- 날짜·장소·규모 선택지별 what-if 비교
- 개최 시기를 앞뒤로 바꿨을 때의 민감도
- 실내·실외, 무료·유료, 예산·홍보 수준 변경 시나리오
- 주차·숙박·화장실·안전 인력 등 편의시설 부족 추정
- 경쟁 행사와 날씨 위험
- 유사 과거 행사와 비교
- 우선 보완할 항목과 예상 영향
- 데이터가 부족해 판단할 수 없는 항목

### 사용자용 출력

- 예상 혼잡도와 시간대·날짜별 상대 혼잡
- 티켓 수요·매진 가능성 등급
- 방문 추천 날짜·시간대
- 예상 대기·주차 부담 등급
- 대중교통·주차·숙박·주변 관광 정보
- 지도에서 비교할 인근 행사와 관광지
- 행사 전후 추천 코스
- 날씨와 혼잡을 반영한 방문 주의사항
- 최신 데이터 갱신 시각과 예측 변동 여부

사용자 화면은 예측 결과를 확정 사실처럼 표현하지 않고 범위·등급·기준 시점과 한계를 함께 표시한다.

## 학습표 기본 구조

한 행은 `행사 × 예측 시점`을 나타내는 것을 권장한다.

```text
event_id
prediction_as_of
event_start_at
region_code
event_type
venue_capacity
tourapi_features...
datalab_history_features...
calendar_features...
weather_forecast_features...
competition_features...
planner_input_features...
label_value
label_type
label_source
```

같은 행사에 `D-30`, `D-7`, `D-1` 행이 있다면 각 행에는 그 시점까지 알 수 있었던 값만 들어가야 한다.

## 학습·검증 순서

1. label 정의와 출처를 확정한다.
2. 같은 지역·월·요일의 평균·중앙값으로 단순 baseline을 만든다.
3. 설명 가능한 규칙 score를 만든다.
4. LightGBM 회귀로 중앙 예측을 학습한다.
5. 가능하면 quantile 목적함수로 예측 범위를 만든다.
6. 과거→미래 시간 분할로 검증한다.
7. 동일 행사·주최자·지역이 학습과 평가에 과도하게 겹치지 않도록 group 검증을 추가한다.
8. MAE·Median AE·RMSLE·혼잡 등급 성능과 baseline 대비 개선을 기록한다.
9. 예측 범위가 실제값을 포함하는 비율과 지역·행사 규모별 오차를 확인한다.
10. baseline보다 의미 있게 좋고 오류 패턴을 설명할 수 있을 때만 제품 기본 모델로 채택한다.

random split만 사용하면 동일한 연례 행사나 같은 지역 패턴이 양쪽에 섞여 성능이 부풀 수 있으므로 최종
근거로 사용하지 않는다.

## 역할 분담 후보

AI 모델은 두 화면이 공유하므로 한 사람만 이해하는 별도 작업으로 만들지 않는다.

| 책임 | 추천 담당 | 작업 |
| --- | --- | --- |
| label·평가지표 결정 | 두 명 공동 | 서비스 표현과 실제 데이터 의미 확정 |
| 수집·학습 pipeline과 model | 공유 데이터·예측 계약 관리자 | feature 생성, baseline, LightGBM, 검증, version 관리 |
| 기획자 입력·what-if 연결 | 기획자 기능 담당 | planner 입력 schema와 모델 입력 연결, 기획자 결과 화면 |
| 캘린더·지도 결과 연결 | 사용자 기능 담당 | 행사별 혼잡·수요 표시와 사용자 결과 화면 |
| prediction API 계약 | 계약 관리자 작성, 상대 담당 검토 | 공통 출력, 오류, 출처와 fallback 정의 |
| 모델 결과 최종 승인 | 두 명 공동 | baseline 비교와 심사 시연 가능성 검토 |

기획자 기능 담당이 모델 관리자를 겸하면 입력→예측→보완점 흐름을 만들기 쉽다. 사용자 기능 담당이 모델
관리자를 겸해도 되지만, 캘린더·지도 작업량과 데이터 pipeline 작업량을 함께 비교한 뒤 정한다.
